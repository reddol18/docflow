# docflow 실습 기록 (2026-10-29)

확인한 것과 확인 방법을 그대로 적는다. 추정은 추정이라고 쓴다.

## 0. 준비
- 맥 colima가 꺼져 있어 다시 켬 (4 CPU / 8GB, k3s v1.35). 은행 게이트웨이 스택은 0개로 줄임 (`free_bank_stack.sh`) → 노드 메모리 사용 1.8Gi.
- 이미지: python 3.11.17-slim + paddlepaddle 3.2.2 / paddleocr 3.3.3 / paddlex 3.3.13 (PoC와 같은 버전),
  langgraph 1.2.18, langgraph-checkpoint-postgres 3.2.0, qdrant-client 1.20.0, openai 3.41.0. OCR 모델은 빌드 때 받아 넣음. 2.0GB.
- Postgres 17.10-alpine, Qdrant v1.19.2. 비밀값(pg 비밀번호, OpenAI 키)은 화면에 찍지 않고 Secret으로만.

## 1. 첫 배포 오류
- `cannot insert multiple commands into a prepared statement`: 체크포인트용 연결 풀을 `prepare_threshold=0`으로 열어서,
  여러 문장짜리 스키마 SQL이 실패 → 한 문장씩 실행하도록 고침.

## 2. 첫 철 (5350109-1997-0002, 13쪽)
- OCR 쪽당 7~11초 (첫 쪽 15.6초, 모델 적재 포함). PoC Windows CPU(약 10초)와 비슷.
- 문서 시작 판별 10/10 (recall·precision 100%).
- 비용 $0.011 (추출 10건, 손글씨 칸 20개, 임베딩 1회).
- 처음 설정(gpt-4o-mini low)으로 손글씨 일련번호가 5/10. 틀린 5건 중 4건은 빈칸으로 답하면서 확신도 0.99~1.0
  → 검토 표시가 안 붙어 '표시 없이 틀린 문서'가 10건 중 5건.

## 3. 손글씨 칸 판독 모델 비교
같은 칸 20개로 지시문·해상도·모델을 바꿔 봄 (`eval/cell_variants.py`, Pod 안에서 실행). 결과는 design.md 5절.
gpt-4.1-mini(high)가 일련번호 7/10, 일자 8/10, 20칸 $0.0026으로 가장 좋고 가장 쌌다 → 채택.
10건뿐이라 결론은 잠정. 전체 680쪽으로 다시 잰다.

## 4. 텍스트 추출 모델·지시문 비교

틀린 사례를 보니 OCR 오독('회담', '필중', '파른')을 gpt-4o-mini가 그대로 옮기고, 제목 끝 "건의"를 빼먹었다.

## 5. 6개 철 중간 채점에서 찾은 것 (129건)
- 문서번호 47%인데 일련번호는 68% → 내 조합 코드 버그. 앞부분을 B 값에서 가져와서 B가 우편번호('우621-363')를 뽑은 경우가 그대로 남음
  → 손글씨 칸 판독의 인쇄 부분('기업 55142')을 먼저 쓰도록 고침.
- 수신 47% (PoC 77%) → PoC의 '잘림' 보정(다음 줄 상호·'대표'를 규칙으로 이어 붙임)을 옮기면서 빠뜨렸음 → 다시 넣음.
  PoC OCR로 확인: 3건 중 2건 복원 ('… 청룡공업사 대표', '… 영풍콘크리트 대표').
- 검토 표시가 틀린 일련번호의 56%, 일자의 23%만 잡음. 비전 판독은 틀려도 확신도가 높다.
  저장된 결과로 미리 계산 (`eval/flag_whatif.py`): B와 손글씨 판독이 다르면 표시('불일치')하면
  일련번호 95% (표시 69%), 일자 46% (표시 27%) → 넣음.

## 6. 전체 실행
- 7개 철 680쪽을 올리고 auto(검토에서 멈추지 않음)로 차례로 실행.
- 5개 철이 0장으로 실행 요청되어 404. 처음엔 port-forward 끊김 탓으로 봤는데(배포 직후 1회는 실제로 끊김),
  진짜 원인은 `run_all.ps1`이 BOM 없는 UTF-8이라 Windows PowerShell 5.1이 한글 원본 경로를 깨뜨린 것.
  업로드 도구가 0장일 때 조용히 넘어가서 늦게 알았다 → 원본 경로는 client.py가 정하고, 0장이면 실패하게 고침. 업로드 재시도도 넣음.
- 5절 수정 3개를 배포하고 7개 철을 다시 auto로 돌림 (12:25 끝). 결과는 design.md 5절.
  일련번호 65%, 일자 79%, 수신 46%, 제목 88%. 표시 없이 틀린 문서 10%.
- 수신이 안 오른 이유를 틀린 사례로 봄: GPT가 결재란 낱말('과장', '국장', '부시장')을 수신으로 고르거나,
  주소를 버리고 상호만 남기거나('(주)남양에너지 대표'), OCR 오독을 그대로 옮김. 잘림 보정은 규칙 값이 B 값으로 시작할 때만 걸려 효과가 작았다.
- 비용 추정 정정: 처음에 680쪽 $0.10이라 했는데 문서 수(450건)를 절반으로 잡았고 모델도 올려서 실제는 한 번에 약 $0.35.

## 7. 사람 검토 시연과 화면 캡처
- 1997-0002 철을 human으로 다시 실행 → validate 뒤 `interrupt()`에서 멈춤 (10건 중 9건 표시). 대시보드에 '검토 대기'로 뜸.
- 캡처는 `NEXT_PUBLIC_MASK_IMAGES=1`로 머리부 이미지를 흐리게 하고 Chrome headless로 찍음. 손글씨 칸 조각(숫자)만 그대로 보인다.

## 8. 부하 시뮬레이션 (breakscale_wrap)
- 시나리오 `sim/a_mac.json`(지금 구성), `sim/b_cloud.json`(클라우드). 결과와 넣은 값은 README "부하 시뮬레이션" 절.
- 실행: `cd <breakscale_wrap>; bun <docflow>/sim/run.ts <docflow>/sim/a_mac.json 300` (`run.ts`, `compress.py`는 bank_llm_gateway에서 가져옴).
  영상은 30배 압축본을 breakscale_wrap의 `lab/scenarios/`에 녹화하는 동안만 복사해 `lab/viz/record.mjs`로 찍고 지웠다.
- 처음엔 B를 breakscale_wrap 자체 오토스케일러(fleet)로 만들었는데, 대기열 → 워커 구조에서 꺼진 워커도 대기열에서 일을 꺼내 가 실패했다(쪽이 사라짐).
  대기열과 워커 사이에 LB를 넣으니 워커가 대기열에서 꺼내 가지 않아 아무것도 처리되지 않았다. 엔진의 worker는 대기열에서 끌어오는 쪽이고 LB는 밀어 넣는 쪽이라서다.
  → 워커 노드 하나의 `instances`를 시각표로 1→6→1 바꾸는 방식으로 KEDA를 근사.
- B 첫 판에서 사양을 노드 1대(4 vCPU)로 적어 화면에 CPU 150%가 떴다. Pod마다 노드가 따로라 vCPU를 6대 합(24)으로 고침. (worker 종류는 CPU 경합 모델 대상이 아니라 처리 결과는 같았다.)
- 몰림 크기가 seed마다 크게 다르다(seed 1 약 210쪽, seed 2 약 130쪽). 도착 간격을 바뀌기 전 속도로 뽑는 탓으로 보임(추정). seed 1로 고정해 보고.
