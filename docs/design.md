# docflow — 공문서 스캔 색인 플랫폼 (프로토타입)

1990년대 공문서 스캔 묶음(철)을 올리면 **문서별로 나누고, 색인 4칸(문서번호·시행일자·수신·제목)을 뽑고,
자신 없는 칸은 사람 검토로 넘긴 뒤, 검색(벡터 + 낱말)과 질문 답변까지** 하는 서비스.
records_poc 3일 PoC(`work/gt/day3_summary.md`)에서 스크립트로 이어 붙였던 단계를 LangGraph 흐름으로 옮겨
쿠버네티스(맥북 k3s) 위의 서비스로 만들었다.

## 1. 구성

```
Windows ─(ssh 터널 → kubectl port-forward)→ docs 네임스페이스 (k3s, 맥북 colima 4 CPU / 8GB)
                                             ├ docflow   FastAPI + LangGraph + PaddleOCR(CPU)   요청 1.5 CPU / 2Gi, 한도 5Gi
                                             ├ postgres  문서 색인 표 · 비용 장부 · LangGraph 체크포인트
                                             └ qdrant    문서 벡터 (text-embedding-3-small, 1536차원, 연도 필터)
                                   바깥으로 나가는 통신: docflow → OpenAI(443)만
```

- 네트워크: 기본 차단 + DNS. docflow → postgres/qdrant, docflow → 공인 IP 443만 연다. postgres/qdrant는 docflow에서만 받는다.
- OCR 모델은 이미지 빌드 때 받아 넣는다 (실행 중 Pod는 모델 서버에 나갈 수 없음). 이미지 2.0GB.
- 은행 게이트웨이 실습(`bank_llm_gateway`)은 같은 클러스터에 그대로 있고, 이 작업 동안 0개로 줄여 둠
  (`scripts/mac/free_bank_stack.sh undo`로 복구). 멀티테넌트·보안·다중 LLM은 다음 단계.

## 2. 흐름 (LangGraph)

철 하나 = 그래프 실행 한 번 (`thread_id` = 철 id). 상태는 노드가 끝날 때마다 Postgres에 저장된다.

```
철:   ocr → split ─(문서마다 Send, 동시 4)→ doc → validate ─(표시 있음 & human)→ review [interrupt] → index
                                                        └(없음 또는 auto)──────────────────────→ index
문서: extract → locate ─(칸 못 찾음 & 더 넓힐 수 있음)→ widen → locate (순환)
                      └→ read → merge
```

| 노드 | 하는 일 | PoC에서 가져온 것 |
|---|---|---|
| ocr | PaddleOCR 3.3.3 한국어, 긴 변 1920. 쪽마다 결과를 파일로 남김 → 다시 돌리면 건너뜀 | `run_ocr.py` 그대로 |
| split | 문서 시작 쪽 판별 (머리부 기관명·우편번호 + 문서번호/시행일자, '별지' 제외) | `gt_draft.analyze` 규칙 |
| extract | 문서 첫 쪽 텍스트 → GPT(gpt-4o-mini)가 4칸 + 확신도, 수신은 규칙 보정 | 추출 프롬프트, `recipient_fix` (목록·참조 규칙) |
| locate / widen | 인쇄된 '문서번호'·'시행일자' 상자 오른쪽 손글씨 칸 위치. 못 찾으면 머리부 범위 40→48→56% | `crop_fields` (PoC는 40% 고정) |
| read | 잘라낸 칸을 GPT 비전(gpt-4.1-mini)으로 판독, 확신도 = 토큰 확률 기하평균 | PoC는 ko-trocr(로컬) |
| merge | B 값의 분류번호 + 손글씨 일련번호, 손글씨 일자 우선 | `hw_flags.build` |
| validate | 검토 필요 표시: 형식·범위·흐름(앞뒤 3건)·확신도 + 수신·제목은 GPT 확신도 < 0.8 | `hw_flags` + 'LLM 표시' |
| review | `interrupt()`로 멈춤 → 검토 화면에서 고친 값이 `Command(resume=...)`로 들어오면 이어 감 | PoC의 검토 화면을 흐름 안으로 |
| index | Postgres upsert + 임베딩 → Qdrant | PoC의 SQLite FTS 대신 |

**왜 LangGraph인가 (그냥 함수 호출이 아니라)**
- 사람 검토에서 몇 시간 멈췄다 이어 가야 한다. 그 사이 Pod가 바뀌어도 상태가 Postgres에 있다.
- 문서마다 병렬(Send)로 돌리고 결과를 reducer로 합친다. 일부 문서가 실패해도 성공한 문서 결과는 체크포인트에 남는다.
- 칸 위치를 못 찾으면 범위를 넓혀 다시 찾는 순환이 그래프에 드러난다.
- 어떤 문서가 어떤 경로를 지났는지(재판독 범위, 표시 종류)가 결과에 남는다 → 자동 처리율을 잴 근거.
- 단계가 2~3개뿐인 일직선 작업이었다면 과했을 것이다.

**역할 나누기:** 철 단위 대기열은 지금은 FastAPI 안의 작업자 1개(OCR이 CPU를 다 씀). 처리량이 필요해지면
어제 게이트웨이처럼 Redis Streams + KEDA로 docflow 작업자를 늘리는 쪽이 자연스럽다 (LangGraph는 "무슨 단계를 어떤 순서로",
대기열은 "언제, 몇 개를").

## 3. API

| | |
|---|---|
| `POST /volumes/{vol}/pages` | 쪽 이미지 올리기 (multipart) |
| `POST /volumes/{vol}/run?review=human\|auto` | 흐름 시작. auto = 검토에서 멈추지 않음(평가용) |
| `POST /volumes/{vol}/resume` | 끊긴 곳부터 다시 |
| `GET /volumes/{vol}`, `/documents` | 상태(다음 노드·검토 대기·비용), 문서별 결과 |
| `GET/POST /review/{vol}` | 사람 검토 화면 → 제출하면 흐름 재개 |
| `GET /search?q=&year_from=&year_to=` | Qdrant 벡터 + Postgres 낱말 결과를 RRF로 합침 |
| `GET /ask?q=` | 상위 5건으로 GPT가 답하고 근거 doc_id를 단다 |
| `GET /graph` | 흐름 그림 (mermaid) |

## 4. 비용

모든 GPT 호출은 Postgres `usage` 표에 토큰·비용을 남기고, 하루 사용액이 `DAILY_BUDGET_USD`(3.0)를 넘으면 호출하지 않는다
(사후 정산이라 동시 호출 몇 건만큼은 넘을 수 있음). 1997-0002 철(13쪽, 문서 10건) 실측: 문서당 약 $0.0005
(추출 $0.0002, 손글씨 칸 2개 $0.00026, 임베딩 $0.00001). OCR은 로컬이라 0.

## 5. 실측 기록

### 전체 680쪽 (7개 철, 정답 164건, `eval/score.py`)
| 항목 | 텍스트 추출(B)만 | 최종 (손글씨 판독·규칙 합침) |
|---|---|---|
| 문서번호 | 30% | 64% |
| 일련번호 | 32% | 65% |
| 시행일자 | 62% | 79% |
| 수신 | 46% | 46% |
| 제목 | 88% | 88% |

- 문서 시작 판별 recall 85/86, precision 100%. 4칸 모두 정답 25%.
- 검토 표시: 일련번호 69% 칸에 표시 → 틀린 것의 98% 포함. 일자 30% 표시 → 49% 포함. 문서 단위로 80% 표시, 표시 없이 틀린 문서 10% (16건).
- 한 번 처리 비용 약 $0.35. 실험·재실행 포함 누적 약 $0.71 + 비교 스크립트 약 $0.2.

### 손글씨 칸 판독 모델 비교 (1997-0002 철 10건, 칸 20개, `eval/cell_variants.py`)

- 틀린 답에도 확신도가 높은 경우가 많다(0.9 이상). PoC 기준값(일련번호 0.9, 일자 0.8)은 ko-trocr 기준이라 다시 맞춰야 한다.

### 검색 첫 기준값 (질의 64개 사람 확인 후, `eval/search_score.py`, 2026-11-06)
질의 세트 `eval/data/search_queries.jsonl` (https://github.com/reddol18/docflow/issues/20): 정확 조회 12·주제 28·바꿔 말하기 6·조건 8·답 없음 10. 450건(김해 7개 철), 임베딩 `text-embedding-3-small`, 후보 30개(`main.CANDIDATES`). 순위는 /search와 같은 `main.ranked()`로 낸다. 조건 질의는 화면 연도 칸을 채운 것처럼 `year_from=year_to=연도`로 잰다. 색인에 같이 있는 시험용 철(`test-flags-…`, 실제 문서 복제 6건)은 정답 세트 밖이라 순위에서 뺀다. recall@k는 정답이 k보다 많으면 k로 나눈다 — 분모가 k마다 달라 recall@5가 recall@10보다 클 수 있으니 @5와 @10을 서로 비교하지 않는다.

읽는 법:
- **정확 조회(문서번호)를 RRF가 망친다.** 낱말만 쓰면 12건 중 11건이 1위인데(나머지 1건 '회계 13330-804'는 부분 일치로 '…-8040'도 걸려 2위), 벡터가 엉뚱한 문서를 올려 RRF에서는 1위 2건·2위 2건·5위 1건, 나머지 7건은 6~10위로 밀린다. 문서번호 꼴 질의는 낱말 1위를 그대로 앞에 두는 규칙이 필요하다.
- **'관련 문서 없음'은 RRF 점수로 가를 수 없고(분포가 겹침), 벡터 1위 유사도로는 어느 정도 갈린다.** 0.43 미만을 '없음'으로 하면 답 없음 10/10을 잡고 답 있음 9/54를 잘못 '없음'으로 본다(그중 7건은 정확 조회 — 위 규칙으로 따로 처리, 나머지 2건은 바꿔 말하기 '나라 땅을 빌려 쓰는 사용료' 0.31, '그린벨트 안 주택 이축 허가' 0.426).
- 사용자가 본 '도로 신설 허가'는 답 없음 질의다(이 450건에 도로 허가 문서가 없음). 벡터 1위 유사도 0.43 미만으로 '없음'에 든다.
- **연도 칸을 쓰면 조건 질의는 세 방식 모두 잘 찾는다.** 연도 칸 없이 질의에만 '1999년'을 쓰면(낱말 나누기가 연도를 뺀다) 같은 세트에서 RRF recall@10 0.875, MRR 0.644였다(시험용 철을 빼기 전 채점) — 질의 속 연도를 연도 칸으로 옮기는 것은 개선 후보.
- **이 수치는 낱말 검색에 유리하게 기울어 있다.** 정답을 제목 규칙으로 뽑았고, 낱말 검색은 제목을 본다. 사람 확인(2026-11-06)에서 64개 중 59개는 그대로, 5개(주제 4·조건 1)에 정답 12건을 더했다(뺀 것 없음). 더하기 전후를 같은 방식으로 재면 벡터만 주제 recall@10 0.871→0.889, MRR 0.900→0.918 — 제목 규칙이 놓친 관련 문서를 벡터가 찾고 있었다. 확인용 화면은 검색 상위 후보를 보여 주므로 후보 밖의 관련 문서는 여전히 빠졌을 수 있다.

## 6. 한계 (지금)
- 정답은 PoC와 같은 김해 7개 철 164건뿐. 외부 양식은 20쪽(9건)만 확인했었다.
- 쪽 이미지에 실명·서명·직인이 있다. 이미지·OCR 결과는 맥 클러스터 PVC와 `work/`(git 제외)에만 둔다.
- 낱말 검색은 형태소 분석 없는 부분 일치. 벡터 검색과 RRF로 합칠 뿐 튜닝은 안 했다.
- 철 대기열이 프로세스 메모리에 있다 → Pod가 죽으면 대기 중이던 철은 다시 걸어야 한다(진행 중이던 철은 `/resume`).
- 사람 검토 화면에 인증이 없다 (port-forward로만 접근).

## 7. 클라우드 이식 (설계, 아직 안 만듦)

맥 k3s 1노드에서 한 Pod·한 DB로 붙어 있던 것을 클라우드로 옮긴다는 가정의 목표 구성이다.
처리량 근거는 README "부하 시뮬레이션" 절의 B안이다(OCR 워커 1~6개, 몰림 끝 → 약 6분).
설계 이슈: https://github.com/reddol18/docflow/issues/16

### 목표 구성

```
브라우저 ─HTTPS/SSE─▶ [노드 그룹 A · 상시, 작게]   Next.js · docflow API (FastAPI, SSE)
                          │  ▲
                넣기(XADD) │  │ 알림(Pub/Sub)
                          ▼  │
                     [관리형 Redis/Valkey]       작업 대기열(Streams) · 토큰/진행 알림(Pub/Sub) · 검색어 임베딩 캐시
                          │  ▲
                꺼내기     │  │ 토큰·진행 발행
                          ▼  │
                     [노드 그룹 B · KEDA 1~N]    OCR·LLM 워커 Pod (taint → 워커만 올라감)
                          │
          ┌───────────────┼──────────────────┐
          ▼               ▼                  ▼
   [관리형 Postgres]   [Qdrant]        [오브젝트 스토리지]
   색인·문서·수정 이력   문서 벡터        쪽 이미지 · 잘라 줄인 이미지
   비용 장부·체크포인트
   진행 이벤트 기록
                                   바깥으로 나가는 통신: 워커·API → OpenAI(443)
```

API도 Postgres·Qdrant·오브젝트 스토리지를 읽는다(검색, 상태 조회, 이미지). 그림에서는 선을 줄였다.

| 저장소 | 두는 것 | 잃으면 |
|---|---|---|
| 관리형 Postgres | 문서 색인·수정 이력·비용 장부(`usage`)·LangGraph 체크포인트·진행 이벤트 기록 | 전체가 멈춤. 원본 기록 |
| 관리형 Redis/Valkey | 작업 대기열(Streams + 컨슈머 그룹), 토큰·진행 알림(Pub/Sub), 검색어 임베딩 캐시 | 대기 중 작업이 사라짐 → 아래 내구성 설정 필요. 알림·캐시는 다시 만들 수 있음 |
| Qdrant | 문서 벡터 (1536차원, 연도 필터) | Postgres 색인에서 다시 임베딩하면 복구 (비용 듦) |
| 오브젝트 스토리지 | 쪽 이미지, `/head`·`/crops`용 잘라 줄인 이미지 | 원본. 지금의 PVC 자리 |

- **분리 단위는 노드 그룹이다.** 구성요소마다 VM을 따로 두지 않는다. OCR이 CPU를 다 쓰므로 워커만 노드 그룹 B에 올리고(taint + toleration·nodeSelector), API가 CPU를 빼앗기지 않게 한다.
- Qdrant를 StatefulSet + 볼륨으로 둘지 관리형으로 둘지는 아직 안 정했다.

### 대기열을 Postgres에서 Redis로 옮기는 이유

처음에는 Postgres `SELECT … FOR UPDATE SKIP LOCKED`로 대기열을, `LISTEN/NOTIFY`로 알림을 만들 생각이었다. 클라우드 구성에서는 Redis로 뺀다.

- **`NOTIFY`는 커밋 때 전역 잠금을 잡는다.** 토큰 스트리밍처럼 알림이 잦으면 동시 스트림이 늘수록 다른 쓰기까지 느려질 수 있다. 알려진 성질이고, 여기서 잰 것은 아니다.
- **`NOTIFY`는 읽기 복제본으로 전달되지 않는다.** 복제본을 붙여도 알림은 주 DB에서만 받는다.
- **장애 범위를 나눈다.** 대기열이 몰릴 때 색인 DB까지 흔들리지 않게 한다.
- **Redis 하나로 대기열과 토큰 통로를 같이 쓴다.** Streams + 컨슈머 그룹 + `XAUTOCLAIM`(죽은 워커 작업 되찾기)과 Pub/Sub이 한 인스턴스에 있다.
  SQS는 토큰 통로가 따로 필요하고, RabbitMQ·Kafka는 이 규모에 운영이 무겁다. KEDA에 redis-streams 스케일러가 있다.
- 로컬(k3s 1노드)에서는 같은 인터페이스를 Postgres로 구현해도 된다(대기열은 `SKIP LOCKED`, 알림은 Pod당 LISTEN 연결 1개).

**대기열 전용 VM을 따로 두지 않는 이유:** Postgres가 멈추면 어차피 전체가 멈춘다(체크포인트·색인이 거기 있음). 대기열만 따로 띄워도 가용성은 오르지 않는다.
분리하는 목적은 부하와 장애 범위이고, 그건 관리형 Redis로 충분하다.

### 요청 흐름

**쪽 OCR 작업** (https://github.com/reddol18/docflow/issues/5)
```
업로드 → 오브젝트 스토리지에 쪽 이미지 → 쪽마다 OCR 작업을 Streams에 넣음
워커(노드 그룹 B)가 꺼냄 → OCR → 결과 저장 → ack   (죽은 워커 작업은 XAUTOCLAIM으로 되찾음)
철의 모든 쪽 OCR이 끝나면 → LangGraph 그래프를 이어 돌림 (split → doc → validate → review → index, 체크포인트는 Postgres)
```
- 지금은 철 하나 = 그래프 실행 한 번이지만, 클라우드에서는 OCR을 쪽 단위로 쪼개 여러 워커가 나눠 갖는다.
- 기동 시 체크포인트가 끝나지 않은 철을 찾아 자동으로 이어 간다.
- 대기열 길이 상한을 넘으면 `429 + Retry-After`로 바로 거절한다.

**검색 답변 `/ask`** (https://github.com/reddol18/docflow/issues/17)
```
브라우저 ──SSE──▶ API
                  ├ Pod당 동시 LLM 스트림 < N : 바로 OpenAI stream=True → 토큰 전달
                  ├ N 이상                   : Streams에 넣고 같은 SSE로 "대기 N번째"(queued) → 차례가 오면 토큰
                  └ 대기열 상한 초과          : 429 + Retry-After
워커(동시 처리 수 = LLM 한도에 맞춤) → 토큰을 약 100ms 단위로 묶어 Pub/Sub 발행 + partial_text에 쌓음
API(SSE를 연 Pod)가 구독 → 브라우저로 전달
```
- 연결은 처음 연 SSE 하나다. 바로 처리든 대기열이든 같은 연결로 끝낸다. 대기 중에는 `queued` 이벤트와 ping을 보낸다.
- 토큰 뿌리기를 Pub/Sub으로 하는 이유: 워커와 SSE를 연 API Pod가 서로 다르다.
- **재연결:** 이벤트마다 `id:`를 붙인다. 브라우저가 `Last-Event-ID`로 다시 붙으면 그 뒤 내용을 `partial_text`(답변)나 Postgres 이벤트 기록(진행 단계)에서 다시 보낸다.
- **취소·재시도:** 연결이 끊기면 작업을 `cancelled`로 표시하고 워커는 시작 전에 확인한다. OpenAI 429·5xx면 작업을 대기열로 되돌리고 `reset` 이벤트를 보낸다.
- **진행 단계:** 이벤트는 지금처럼 Postgres에 기록하고, 기록할 때 Pub/Sub에도 알린다. 기록과 알림을 나눠서, Redis가 비워져도 기록으로 이어 간다.
- **비용 한도:** API·워커 Pod가 여러 개라 Pod 메모리로 예약할 수 없다. 예약·정산은 Redis 원자적 증가(`INCRBYFLOAT` + 날짜 키 만료)나 Postgres 행 잠금으로 한다 (https://github.com/reddol18/docflow/issues/7).

### KEDA 증설·축소

- KEDA redis-streams 스케일러로 대기열 길이에 따라 워커 1~N개. 노드 그룹 B도 같이 늘고 준다.
- README B안의 값: 증설 대기 110초(KEDA 감지 30초 + 노드 준비 + 2GB 이미지 + 모델 적재), 대기열이 빈 뒤 5분에 축소. 둘 다 [가정].
- 워커를 12개 넘게 늘리면 그다음 병목은 GPT 동시 호출 수와 계정 분당 한도다(README 시뮬레이션). 워커 상한은 그 아래로 둔다.

### Redis 내구성 (필수)

- 관리형이면 Multi-AZ 복제 + 자동 장애 조치를 켠다. 직접 운영하면 AOF 영속화를 켠다.
- 없으면 Redis 재시작 때 대기열이 사라진다. 지금 Pod 메모리 대기열의 문제(https://github.com/reddol18/docflow/issues/5)가 그대로 재발한다.
- 알림(Pub/Sub)과 캐시는 잃어도 된다. 기록은 Postgres에 있다.

### 폐쇄망 배포와의 관계

현장 공고는 폐쇄망·인터넷 불가 조건이 많다(https://github.com/reddol18/docflow/issues/13). 관리형 서비스를 쓸 수 없으니 방향이 다르다.
구성요소 인터페이스는 같게 두고 배포만 둘로 나눈다.

| | 클라우드 | 폐쇄망 |
|---|---|---|
| 대기열·알림 | 관리형 Redis/Valkey (Streams·Pub/Sub) | Postgres(`SKIP LOCKED`·`LISTEN/NOTIFY`) 또는 직접 띄운 Redis(AOF) |
| DB | 관리형 Postgres | 클러스터 안 Postgres (지금처럼) |
| 이미지 저장 | 오브젝트 스토리지 | 로컬 PVC |
| LLM·임베딩 | OpenAI | 로컬 모델 (Ollama·vLLM 등 OpenAI 호환) |
| 한도 | 일일 비용 한도 | 동시 처리 수 한도 |
| 네트워크 경계 | 보안 그룹 | NetworkPolicy (외부 송신 0) |

**같은 것:** LangGraph 흐름과 체크포인트, 대기열 인터페이스(넣기·꺼내기·완료·되돌리기·길이·순번), SSE 이벤트 형식, Qdrant, API.
