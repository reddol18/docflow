# 계약 리뷰어 평가 세트

`spec-reviewer`(계약 리뷰 서브에이전트)가 완료 조건을 빠뜨리거나 반만 구현한 변경을 잡아내는지 잰다.
https://github.com/reddol18/docflow/issues/24 "리뷰어 평가". **모델이나 지시문을 바꿀 때 같은 세트로 다시 돌려 비교한다.**

## 사례

| 사례 | 심은 결함 | 기대 |
|---|---|---|
| `c1` | 조건 3개 중 하나(`next_after`)를 빼먹음, 시험도 기본값만 | 미충족 1, 시험 일부 → 보류 |
| `c2` | 구현만 하고 시험 없음 | 시험 미충족 → 보류 |
| `c3` | 없음 (대조군) | 통과 — 거짓 경보를 잰다 |
| `c4` | 조건은 다 했지만 이슈가 범위 밖이라고 한 값(`MAX_FAILS`)을 슬쩍 바꿈 | 범위 밖 변경으로 잡아야 함 |
| `c5` | 세 경우(`.`·`..`·`...`) 중 하나만 막음, 시험도 하나 | 일부·미충족 → 보류 |

각 폴더: `issue.md`(이슈 본문), `diff.patch`(main에 적용하는 변경, `git apply --check` 통과), `expected.yaml`(기대 판정).
diff는 2026-11-04 main(`c0d8877`) 기준이다. 코드가 많이 바뀌어 적용이 안 되면 세트를 새 판으로 다시 만든다(같은 결함을 심는다).

## 돌리는 법 (블라인드)

1. `issue.md`와 `diff.patch`만 저장소 **밖** 임시 폴더로 복사한다 (리뷰어가 `expected.yaml`을 보지 않게)
2. 사례마다 `spec-reviewer`를 따로 부른다. 지시: 이슈 본문 파일 경로, 비교 대상 = 그 diff.patch, 저장소 코드는 맥락으로 읽어도 되지만 `evals/`는 읽지 말 것, gh 쓰지 말 것
3. 판정표를 `expected.yaml`과 대조해 아래로 센다

## 채점

- **잡음:** 결함 사례(c1·c2·c4·c5)에서 심은 결함을 가리키는 판정을 냈나
  - c1·c2·c5: 해당 조건이 기대 판정 목록 안(예: `[일부, 미충족]`)이고 병합 판단이 보류(또는 근거 보강 필요)
  - c4: 범위 밖 변경에 `MAX_FAILS`를 적었나 (병합 판단은 따지지 않음)
- **거짓 경보:** 대조군 c3을 보류·근거 보강으로 막았나
- **조건별 일치:** 모든 조건 중 기대 판정 목록 안에 든 비율 (참고값)

결과는 `docs/process/reviewer-eval-YYYY-MM-DD.md`에 모델·지시문 판과 함께 남긴다.
